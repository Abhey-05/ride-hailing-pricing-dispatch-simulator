# Changelog

Major implementation decisions and calibration fixes, in the order they happened. This is the honest paper trail for "how did you know your simulation was correct?"

## Phase 1 — Product & architecture

- Chose file-based (Parquet/CSV) result storage over Postgres, and Streamlit+Plotly over a React dashboard, to keep the build tractable within scope while still documenting the "production path" (Postgres schema, API docs) for credibility.

## Phase 2 — Mathematical specification

- Designed the full timestep sequence, demand/pricing/dispatch/cancellation math, and experiment design before writing any simulation code (`docs/MATHEMATICAL_MODEL.md`, `docs/EXPERIMENT_DESIGN.md`, `docs/ASSUMPTIONS.md`).
- Re-designed the experiment matrix from a naive `4×5×6×4=480` grid to `4×5×24 seeds=480` (core, single scenario) + `600` robustness runs across the other 5 scenarios — chosen because 24 paired seeds gives real statistical power for the primary hypothesis test, whereas 4 seeds spread across 120 cells would not.

## Phase 3 — Engine implementation

- **Bug found & fixed (calibration):** initial `grid_scale_km = 3.0` produced a city with a ~34 km diagonal. Combined with a fleet of 260 drivers spread across 10 zones, this made typical pickup ETAs 20–50 minutes — far outside the range the rest of the model (5-minute wait reference, 4–8 minute rider patience) was calibrated for. This crushed driver acceptance probability toward zero (observed acceptance rate: 11%) and completion rate to 34%, with an unrealistic 43% cancellation rate. **Fix:** reduced `grid_scale_km` to `1.2` (≈13.6 km diagonal), bringing typical pickup ETAs into the 3–8 minute range. Updated `docs/MATHEMATICAL_MODEL.md` and `docs/ASSUMPTIONS.md` to match. Post-fix baseline (NORMAL / BASIC_SURGE / NEAREST_DRIVER, seed 0): 69% driver acceptance, 54% completion rate, 22% cancellation rate, P90 wait 11 min — all directionally sane.
- **Bug found & fixed (bootstrapping failure):** the driver-acceptance normalizers (`avg_pickup_eta_city`, `avg_fare_driver_share_city`) were only updated via EMA when a driver *accepted* an assignment. Since a too-low initial default value crushed acceptance probability near zero, the EMA had no successful matches to learn from and never corrected itself — a self-reinforcing failure. **Fix:** normalizers now update via EMA on every dispatch *offer*, not just accepted ones, so they reflect the true offered distribution regardless of the current acceptance rate.
- **Design fix (double-booking risk in look-ahead dispatch):** `ETA_OPTIMIZED` and `ADVANCED_HEURISTIC` can offer a still-busy (`ON_TRIP`) driver who is about to free up nearby. The first implementation immediately transitioned such a driver to `EN_ROUTE_TO_PICKUP` for the new request, silently abandoning their current trip — a real correctness bug. **Fix:** added a `queued_request_id` / `queued_pickup_travel_min` pair on `Driver`; a look-ahead match is "pre-booked" and only takes effect when the driver's current trip actually completes (engine.py step 3). Post-match cancellation on a still-queued request now correctly leaves the driver's current trip untouched rather than erroneously freeing them. Covered by `tests/test_engine_invariants.py::test_no_double_booking_including_lookahead_policies`.
- **Empirical finding, not a bug:** Validation Plan check #5 ("nearest-driver minimizes pickup distance") turned out to be false in the unqualified form originally written — `ETA_OPTIMIZED` and `ADVANCED_HEURISTIC` can achieve a *lower* average realized pickup distance than `NEAREST_DRIVER`, because their look-ahead candidate set (drivers about to free up nearby) is strictly larger than "currently idle only." The check was refined to compare `NEAREST_DRIVER` only against the other available-only policies (`DRIVER_EARNINGS_AWARE`, `MARKETPLACE_AWARE`), where it does hold exactly. Documented in `docs/EXPERIMENT_DESIGN.md` Section U.
- Chose **absolute `release_tick` bookkeeping** over countdown-timer decrementing for trip/pickup phases — behaviorally identical to the spec's "decrement then resolve" language, simpler and less error-prone to implement.
- Chose to resolve `ASSIGNED → {EN_ROUTE_TO_PICKUP | AVAILABLE}` synchronously within a single tick rather than persisting an observable `ASSIGNED` state across ticks — the spec's step 8/9 sequence describes dispatch and driver-acceptance resolution happening back-to-back in the same tick, so no information is lost.

## Phase 4 — Validation

- Full pytest suite (22 tests) covers: reproducibility (bit-identical output for the same seed), all ten Validation Plan checks from `docs/EXPERIMENT_DESIGN.md` Section U, and every "invariant that must never break" from Part 42 of the project brief (no negative price, surge within cap, utilization bounded, no double-booking, driver earnings ≥ 0, completed ≤ requested).

## Phase 6 — Full experiment matrix

- Ran the full 1,080-run matrix (480 core + 600 robustness) in 327s wall-clock, single-threaded, on a laptop -- confirmed the "6 minutes" runtime estimate from a 60-run timing probe.
- Results saved to `results/results.csv` / `.parquet` plus `results/manifest.json` (seed lists, versions, wall-clock time) for reproducibility.

## Phase 7 — Statistical analysis & charts

- Built `src/analysis.py`: paired bootstrap CI (10,000 resamples), paired Wilcoxon + t-test, matched-pairs Cohen's d, and a pre-registered practical-significance bar (≥5% relative effect AND CI excludes 0) applied uniformly to every comparison -- decided in `docs/EXPERIMENT_DESIGN.md` Section Q *before* the experiment ran, not fit to the results afterward.
- Headline, unmanipulated finding: `ETA_OPTIMIZED` beats the `NEAREST_DRIVER` baseline on P90 wait in every one of the 4 pricing policies (7.8%-11.3%, all p<0.001), with driver earnings and platform revenue both *improving* rather than trading off. Full writeup: `docs/EXPERIMENTS.md`.
- Equally important negative finding, also unmanipulated: `ADVANCED_HEURISTIC` -- the policy combining the most objectives -- performed *worse* than the naive baseline in every configuration. Root-caused to its hand-tuned weights over-prioritizing marketplace-imbalance/cancel-risk terms relative to pickup ETA (`src/config.py::ADVANCED_HEURISTIC_WEIGHTS`). Reported as-is rather than re-tuned after the fact, since re-tuning post-hoc to fix an inconvenient result would defeat the point of pre-registering a decision framework.
- **Bug found & fixed:** `pandas.DataFrame.fillna(method="ffill")` no longer exists in pandas 3.0 (used in the zone-heatmap chart) -- replaced with `.ffill()`.

## Phase 8-9 — Dashboard & API

- Streamlit dashboard (`dashboard/app.py`) and FastAPI service (`api/main.py`) both read directly from `results/*.csv` / call `src.engine` -- no separate business logic duplicated between them.
- **Bug found & fixed:** `api/main.py`'s `/simulation/run` endpoint raised `ValueError: Out of range float values are not JSON compliant: nan` for any run with too few completed trips (e.g. a short horizon starting at midnight, before most driver shifts begin) -- Starlette's default `JSONResponse` only auto-sanitizes NaN for explicitly float-typed Pydantic fields, not values inside a generic `dict`. Fixed with an explicit `_sanitize_nan` pass before constructing the response. Found by `tests/test_api.py`, not by inspection.
- Both the dashboard (via `claude-in-chrome` browser automation) and the API (via direct HTTP calls) were actually exercised end-to-end, not just started and assumed to work.

## Phase 10 — ML component & AI copilot

- Added a genuine ML use case: predicting whether a ride request will cancel, using only pre-dispatch, request-creation-time features (segment, patience, surge, price, distance, marketplace imbalance, hour of day) -- deliberately excluding any post-match field (pickup ETA/distance), since those only exist *because* a match happened, which would leak the label.
- Real result (`train_cancellation_model.py`, ~149k request-level training rows from live simulations): a naive single-variable "shorter patience = higher risk" rule scores AUC 0.55 (barely better than chance); a full-feature logistic regression scores 0.78; gradient boosting scores 0.82. Feature importance shows **time of day and marketplace imbalance dominate patience** (0.75 + 0.17 vs. 0.05 combined importance) -- the actual driver of cancellation risk in this simulation is *when/where* you request a ride, not *who* you are, which the existing single-variable heuristic almost entirely misses.
- AI Marketplace Analyst (`src/ai_copilot.py`, `src/copilot_tools.py`): Claude tool-calling over 5 deterministic functions (pre-computed result lookups + live what-if simulation). The LLM never computes a metric itself.
- **Bug found & fixed:** the first draft of `simulate_whatif`'s demand/supply multiplier override was silently a no-op -- `world.generate_world` only ever looked up `config.SCENARIOS[scenario_name]` internally, so a locally-modified `Scenario` object passed to the engine never actually changed how many requests were generated. Fixed by adding a `scenario_override` parameter to `world.generate_world` itself. Caught by `tests/test_copilot_tools.py::test_whatif_demand_override_changes_request_volume` actually asserting the request count changes, not just that the call succeeds.
- Not runnable end-to-end in this environment (no `ANTHROPIC_API_KEY` present in the sandbox this was built in) -- code is complete and unit-tested at the tool-function layer; the Claude tool-calling loop itself needs a live key to exercise.

## Post-review — AI copilot verified live, made provider-agnostic in practice (not just in theory)

- The user provided a Groq API key (no Anthropic key was available). Rather than only supporting the one provider the code happened to be written against, refactored `src/ai_copilot.py` to route through either Anthropic's `tool_use`/`tool_result` content-block API or Groq/OpenAI-style `tool_calls`/`role:"tool"` messages, sharing the identical `SYSTEM_PROMPT`, `TOOLS` schema (converted once via `_openai_style_tools()`), and `src/copilot_tools.py` functions -- provider selection via `AI_PROVIDER` env var or auto-detected from whichever key is set (`resolve_provider()`).
- **Real bug found and fixed during first live run:** the default Groq model (`llama-3.3-70b-versatile`) returned a 404 `model_not_found` for this account. Diagnosed by querying `client.models.list()` for what was actually available, not by guessing -- switched the default to `openai/gpt-oss-120b`.
- **Security incident during setup, handled directly rather than ignored:** the user's `.env` file initially had a stray space after `GROQ_API_KEY=`, which caused `source .env` to treat the key as a command to execute -- bash's "command not found" error printed the raw key into the conversation transcript. Flagged immediately, the user was advised to rotate the key, and the `.env` parsing was fixed via `sed` without ever re-typing the key value. `ask_copilot.py` also gained a minimal built-in `.env` loader (no new dependency) so this class of shell-quoting mistake isn't needed at all going forward -- the file just needs to exist with `KEY=value` on one line.
- Ran 4 real questions end-to-end through the live Groq-backed copilot, checked each answer against this project's own documented ground truth (`docs/EXPERIMENTS.md`, `docs/ASSUMPTIONS.md`), and saved the verbatim transcript to `docs/AI_COPILOT_TRANSCRIPT.md` -- closing the one remaining open item from `docs/CRITICAL_REVIEW.md` #6.

## Phase 14 — Decision-intelligence layer (Marketplace Health, guardrails, counterfactual, map)

- **Bug found & fixed:** `src/charts.py`'s `demand_and_supply_over_time()` and `wait_distribution()` hardcoded `"NORMAL scenario, seed=0"` in their titles regardless of which scenario/seed the dashboard actually ran -- picking `PEAK_DEMAND` in the sidebar still showed a chart claiming to be `NORMAL`. Fixed by threading an optional `src/sim_context.py::SimulationContext` through every chart builder that names a run, so the label is derived once from the actual run parameters rather than reconstructed ad hoc in multiple places.
- Added `src/decision.py`: a **Marketplace Health Score** (4 weighted dimensions -- Rider Experience, Driver Experience, Marketplace Efficiency, Business Performance -- each a documented blend of metrics normalized via `NORMALIZATION_BANDS`, the empirical 5th/95th percentiles of `results/results.csv` across all 6 scenarios, not arbitrary targets); absolute + baseline-relative guardrail evaluation (the latter generalizes `src/analysis.py`'s existing decision-table guardrail logic to any candidate/baseline pair); a policy `recommend_policy()` sourced entirely from the pre-computed experiment matrix (instant, no live simulation); and `run_counterfactual()`, which runs a **real, live, paired simulation** (common random numbers, same `src.analysis.paired_diff_stats` machinery as the 1,080-run matrix) for whatever specific change is being considered, with a genuine bootstrap CI and Wilcoxon p-value -- not an estimate.
- Added `src/zone_state.py`: per-zone spatial marketplace state (demand, supply/demand ratio, wait, cancellation, surge) aggregated from data the engine already produces (per-request zone + existing per-tick `available_by_zone`/`outstanding_by_zone` timeseries) -- no engine changes. Backs a new synthetic-city **Marketplace Map** (Plotly scatter on the existing zone x/y grid, `src/charts.py::marketplace_map`, 7 selectable metrics) and a zone click-through detail panel with a rule-based (non-LLM) causal explanation (`explain_zone`).
- Redesigned `dashboard/app.py`'s Overview page around the health score, an explicit current-vs-baseline distinction (baseline is now a sidebar control, defaulting to `config.BASELINE_PRICING`/`BASELINE_DISPATCH`), the recommendation card with a "Run Counterfactual" button, the map, and a policy-tradeoff scatter -- with the full per-zone table and guardrail detail moved into a collapsed "Advanced" expander (progressive disclosure) rather than shown all at once. Redesigned the Experimentation tab the same way: best-policy card and "why was this selected" first, full 1,080-row matrix moved into an "Advanced Analysis" expander.
- Verified live in a real browser session (not just unit tests): ran `PEAK_DEMAND`, confirmed every label matches, clicked "Run Counterfactual" and got a live 8-seed paired comparison with real CIs, checked all 4 guardrail badges, and walked the map's zone click-through on both a healthy and a severely-undersupplied zone.
- 15 new tests (`tests/test_decision.py`, `tests/test_zone_state.py`) covering health-score bounds, guardrail pass/fail, counterfactual reproducibility (same policy vs. itself -> zero effect), and zone aggregation invariants (per-zone request counts sum to the total, supply-shortage scenario produces lower average supply/demand ratio than normal). Full suite: 58 passed.
- Not yet done (explicitly out of scope for this pass, not silently skipped): demand/ETA forecasting models, a learned policy-optimization layer beyond the matrix lookup, and wiring `src/ai_copilot.py` into the dashboard itself (it remains CLI-only via `ask_copilot.py`) -- all flagged as Phase 2/3 follow-ups.

## Phase 15 — ML forecasting layer, AI Copilot dashboard tab, closing the Phase 2/3 items above

- Added `src/ml_demand.py`: near-term (15-minute-window) zone-level demand forecasting. Framed deliberately narrow -- an ops team doesn't need a whole-day forecast, they need "is the next 15 minutes about to get worse here." Same leakage discipline as `src/ml_cancellation.py` (only lag/time/supply features known at the window's start); split by whole simulated day, not by row, since same-day windows are autocorrelated. Real result: GBM MAE 2.35 vs. a "same as last window" naive baseline's 3.01 (R² 0.70 vs. 0.48); `lag_1`/`lag_2` dominate feature importance, as expected for Poisson-driven demand.
- Added `src/ml_wait_time.py`: predicts a rider's **realized** wait (request→pickup), not the simulator's quoted pickup ETA. **Deliberate framing decision, not an oversight:** this simulator's pickup ETA (`src/dispatch.py::eta_minutes`) is an exact deterministic function of distance and time-of-day congestion -- there is no noise for a model to learn there, so "predict the ETA formula" would not be a real ML task. Realized wait *is* genuinely stochastic (depends on marketplace imbalance, surge, matching queue) and not visible in a naive distance-only ETA, which is the actual gap section 13 of the brief was pointing at. Real result: GBM MAE 2.75 min vs. a naive distance/speed ETA's 8.12 min (P90 error 5.5 vs. 17.1 min); `imbalance_at_request` alone accounts for 61% of feature importance -- confirms the project's own recurring finding that marketplace imbalance, not trip distance, drives rider pain.
- Both models persist a production pipeline (fit on ALL data, not just the eval split) to `models/*.joblib` via `train_demand_model.py` / `train_wait_time_model.py`, for **live inference without retraining**.
- Wired both as two new AI-copilot tools -- `forecast_demand` and `forecast_eta` (`src/copilot_tools.py`, registered in `src/ai_copilot.py::TOOLS`) -- each grounded in a real live simulation run up to the requested hour (recent-demand lags, available drivers, or averaged real marketplace conditions), with the trained model supplying the actual number. Verified live end-to-end via Groq: a compound question ("how much demand, and how long will a rider wait, in Downtown at hour 9 during PEAK_DEMAND") correctly triggered both tools and cited both `models/*.joblib` sources.
- Extended `src/decision.py::recommend_policy()` to report **both** "best overall" (unconstrained utility) and "best under guardrails" as distinct fields, per the explicit PM framing in the brief ("these are not necessarily the same") -- when they differ, the dashboard's recommendation card now shows which guardrail rejected the higher-utility candidate and by how much, instead of only ever showing the constrained winner.
- Refactored `src/ai_copilot.py`'s internal `_ask_anthropic`/`_ask_groq` to also return a structured tool-call trace (name, input, result per call), exposed via a new `ask_with_trace()`; `ask()` is now a thin wrapper for backward compatibility with `ask_copilot.py`. This is what lets the dashboard show its work instead of an opaque chatbot answer.
- Added the **AI Copilot dashboard tab**: a chat interface over `ai_copilot.ask_with_trace()`, with example questions from the brief's own list, and every answer's tool-call trace shown in an expander (tool name, exact input, full JSON result) -- directly satisfying "the AI must interact with the existing system through tools, never invent a number."
- **Bug found & fixed:** the dashboard's AI Copilot tab initially reported "no LLM API key found" even with a valid key in `.env`, because (unlike `ask_copilot.py`) `dashboard/app.py` never loaded `.env` into the Streamlit process's environment. Fixed by extracting the `.env`-loading logic (previously duplicated inline in `ask_copilot.py`) into a shared `src/env_utils.py::load_dotenv()`, called from both entry points. Found by actually launching the dashboard in a real browser and clicking the tab, not by inspection.
- Verified the full new question set live in a real browser session (not just unit tests): root-cause ("why might cancellations be high during PEAK_DEMAND") produced a real evidence-cited answer with an inspectable 2-call tool trace; "what happens if we remove surge" produced a real markdown comparison table sourced from `results/results.csv`; an intentionally-compound, ambiguous question correctly hit the max-tool-turn limit and reported that honestly rather than fabricating an answer -- confirming the guardrail against overconfident responses actually holds under real model behavior, not just in the system prompt.
- 21 new tests (`tests/test_ml_demand.py`, `tests/test_ml_wait_time.py`, `tests/test_env_utils.py`, plus additions to `tests/test_copilot_tools.py`) covering dataset construction, leakage-safe day-level splitting, baseline-beating assertions, and both new copilot tools against the actual saved models. Full suite: 79 passed.
